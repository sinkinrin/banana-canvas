# Banana Canvas 路线图

更新时间：2026-07-23

## 产品方向

Banana Canvas 的核心仍是“提示词节点 → 图片节点 → 继续引用生成”的可执行工作流。现有 React Flow、Zustand/zundo、项目快照与图片资产体系已经适合表达生成关系，不计划为了获得自由绘图能力而整体替换为 tldraw。

后续画布演进采用“双层能力”思路：保留工作流图作为生成与溯源主模型，在其上逐步补充更轻量的页面组织、图片占位区、批注和展示能力。任何自由画布能力都必须能与生成节点、资产 ID 和项目持久化稳定关联。

## Cowart 样本调研

本次调研基于仓库中保留的 `canvas/` 样本，而非对 Cowart/tldraw 全部能力的推断。样本包含：

- `pages/manifest.json`：独立的页面清单，页面有稳定 ID、名称、排序与相对文件路径。
- `pages/page/cowart-canvas.json`：tldraw schema/store，页面内包含图片、文字、Frame、箭头及图片资产记录。
- `cowart-view-state.json`：当前页面和 camera 独立保存，不混入页面内容。
- `cowart-selection.json`：选中形状及其关联资产的独立交换数据。
- `pages/page/assets/`：原始图片文件；画布 JSON 仅保存相对 URL、尺寸、MIME 和来源元数据。
- 语义化 `meta`：区分 AI 图片占位区、独立生成结果、批注箭头，并保留生成提示词和资产来源。

样本中特别值得关注的交互是：Frame 可被标记为 AI 图片占位区；生成图片作为普通图片形状插入；红色箭头可被标记为批注；选中内容能够连同资产信息形成明确的工具输入。这些语义标记比某个具体渲染库更值得借鉴。

## 值得借鉴

| 能力 | 对 Banana Canvas 的价值 | 建议做法 |
| --- | --- | --- |
| 页面清单与页面文件分离 | 一个项目可以容纳探索、精选、交付等多个空间，避免单张无限画布持续膨胀 | 项目元数据维护页面 ID、名称、顺序；每页独立保存节点、边和视口 |
| 内容状态与视口状态分离 | 移动画布/缩放不应触发完整内容快照和大 JSON 保存 | 独立、节流保存 viewport；内容保存继续走现有项目仓储层 |
| 文件资产与画布元数据分离 | 与现有 `assets/` 方向一致，可进一步减少 Base64、支持缩略图与懒加载 | 沿用稳定 asset ID，增加二进制读取 API、缩略图和 Blob URL 生命周期 |
| AI 图片占位区 | 先规划版式与比例，再把生成结果填入目标区域，比“生成后再整理”更自然 | 新增轻量 `imageSlot` 节点/容器，支持比例、标题、状态和“生成到这里” |
| 显式语义元数据 | 工具无需靠颜色或形状猜测意图，便于自动化和未来插件调用 | 为节点/批注定义版本化 `kind`、`source`、`prompt`、`targetId` 等字段 |
| 批注箭头和文字 | 可直接指出重绘区域或修改意图，适合接入现有 mask edit | 先实现绑定到图片节点的批注层，再把批注转换为编辑提示与可选 mask |
| 选中内容的结构化交换 | “对当前选中图片执行 AI 操作”上下文明确 | 提供只读 selection context：节点、关联资产、提示词、来源链，避免复制大图数据 |
| Frame/分区组织 | 对比方案、故事板和交付版式比纯自动布局更灵活 | 实现工作流分组/画框，而不是立即开放所有自由绘图形状 |

## 应舍弃或延后

- 不整体迁移到 tldraw。当前连线代表真实的生成依赖，React Flow 的节点/边模型、自动布局和既有测试更契合产品核心；双引擎迁移会同时放大交互、序列化和历史兼容成本。
- 不直接持久化第三方库的完整 store/schema。应保存 Banana Canvas 自己的版本化领域模型，渲染层可替换，迁移边界也更清晰。
- 不优先实现钢笔、几何图形、富文本排版等通用白板全家桶。它们只有在能服务图片生成、批注或交付排版时才进入范围。
- 不把完整 selection 副本长期写盘。Cowart 样本中的选择文件适合工具交换，但 Banana Canvas 应默认只保存稳定 ID；需要跨进程传递时再按需解析资产。
- 不复制频繁产生的临时视口快照文件。采用原子写入、单个正式状态文件或现有仓储协议，并设置节流与关闭时刷新。
- 不依赖视觉约定表达语义，例如“红箭头就是批注”。颜色只是表现，业务含义必须是显式、可版本化字段。
- 多人实时协作、CRDT 和通用插件生态暂不进入近期范围；当前本地优先、单用户桌面场景应先把数据模型和性能做好。

## 分阶段落地

### P0：视口状态与数据协议地基

目标：降低无业务内容变化时的保存成本，并为页面、分组和批注预留稳定模型。

- 在项目快照协议中增加 `schemaVersion`，为后续迁移建立单一入口。
- 将 viewport（x、y、zoom）从节点/边内容变更中解耦，按页面节流保存并在重新打开时恢复。
- 为节点扩展可选的版本化语义字段，避免把业务标记散落在组件私有状态中。
- 明确资产记录只引用 asset ID；推进独立二进制读取、缩略图和 Blob URL 懒加载设计。

验收标准：仅平移/缩放画布不重写完整节点快照；重启后恢复最后视口；旧项目无需人工操作即可迁移；迁移与异常数据有单元测试。

### P1：多页面项目

目标：让同一创作项目拥有多个独立工作区，同时共享项目级资产。

- 增加页面清单：稳定 ID、名称、排序、创建/更新时间和当前页面。
- 支持新增、重命名、复制、排序和可恢复删除页面。
- 节点/边/viewport 按页保存，图片资产维持项目级去重和引用计数。
- 导入导出包含页面清单与所有页面；保留单页旧项目兼容。

验收标准：页面切换不丢失未保存内容；复制页面不会重复复制相同图片二进制；删除页面不会误删其他页面仍引用的资产；至少覆盖保存、重启恢复和旧项目迁移测试。

### P1：AI 图片占位区

目标：支持“先安排画面位置与比例，再定向生成/替换”。

- 新增图片占位节点，包含名称、目标比例、可选尺寸、生成状态及当前结果 asset ID。
- 允许从空白占位区创建提示词，或把现有提示词/图片结果填入占位区。
- 替换结果时保留来源链和历史版本，提供对比/回退入口。
- 占位区和普通生成节点共享 Provider 参数与错误/取消处理，不新建第二套生成管线。

验收标准：用户可创建指定比例的占位区并直接生成到其中；失败不会破坏上一张结果；生成关系、prompt 和资产来源可追溯。

### P2：图片批注与定向编辑

目标：把“这里要改什么”直接留在图片附近，并复用现有 mask edit。

- 为图片节点提供可开关的批注层，第一版支持箭头、矩形/自由框和短文本。
- 批注保存结构化目标节点 ID、归一化坐标、类型、文字与创建时间，而非仅保存屏幕像素坐标。
- 支持将一个或多个批注汇总为编辑提示；用户确认后再进入 mask 编辑或生成请求。
- 批注与图片版本绑定；图片被替换时明确选择继承、隐藏或删除，避免错位。

验收标准：缩放、移动和重新打开项目后批注仍对齐；批注不会被误当作工作流边；发送生成前可预览最终提示和 mask。

### P2：Frame、分组与展示模式

目标：在不削弱工作流关系的前提下支持方案对比和交付排版。

- 增加可命名、可调整尺寸的 Frame/分组，节点可归属其中且移动 Frame 时保持相对位置。
- 支持聚焦 Frame、按 Frame 导出预览，以及将 Frame 设为自动布局边界。
- MiniMap、适应视口和自动布局识别 Frame；工作流边可以跨 Frame，但需保持清晰。

验收标准：分组移动不改变生成依赖；导出范围与视觉边界一致；大画布中折叠/聚焦 Frame 可减少无关渲染。

### P3：结构化选择上下文与自动化接口

目标：让内置 AI 操作或未来工具可靠理解用户当前选择。

- 建立 selection context，只暴露选中节点 ID、类型、语义元数据、关联资产 ID、prompt 与来源链。
- 对资产二进制采用按需、受限读取，不把 Base64 放入常驻选择状态或日志。
- 为“用选中图片作参考”“修改选中区域”“总结当前分支”等动作提供统一命令边界。
- 自动化写入必须经过领域命令和 schema 校验，不允许直接改写底层 React Flow 状态。

验收标准：同一选择可被 UI 动作和自动化调用复用；缺失/过期资产返回明确错误；所有写操作可撤销并进入正常持久化流程。

## 架构约束

- 领域模型优先：页面、节点、边、Frame、批注、资产和视口均由 Banana Canvas 定义版本化格式，React Flow 只承担渲染与交互适配。
- 单一资产身份：工作流节点、占位区、批注目标和自动化上下文均通过 asset ID/node ID 关联，不复制图片正文。
- 历史分层：内容编辑进入 undo/redo；临时选择、悬停和连续 camera 变化不进入内容历史。
- 原子与可恢复保存：页面清单、页面内容和视口分别写入时，要能从中断写入恢复；删除继续采用可恢复策略。
- 渐进兼容：每次协议变化必须带迁移器、旧格式 fixture 和往返测试，禁止一次性重写用户项目。
- 性能预算：页面切换、Frame 聚焦和缩略图加载均不得要求预解码项目内全部原图。

## 推荐实施顺序

先完成 P0 的协议、视口和资产基础，再实现多页面；随后以 AI 图片占位区验证新的语义节点模型。批注应建立在稳定的图片版本/资产引用上，Frame 与自动化接口最后推进。这个顺序能优先解决当前完整快照与大资产开销，同时避免为了通用白板能力偏离 AI 图片工作流主线。
