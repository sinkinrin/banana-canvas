## 需要修复的问题

### R1 · 低优先级（已纠正原评级） · 超长项目名保存成功后，项目从列表消失

位置：`src/lib/projects.ts:13`、`src/lib/projects.ts:24`；`src/lib/localProjectStore.ts:155`、`:566`；`src/components/projects/ProjectNameDialog.tsx:65`。

创建、改名和输入框均未限制名称长度，但读取项目索引时只接受名称不超过 200 字符的记录。把已有项目改成 201 字符的名称，改名返回成功，随后索引会过滤该项目，`loadProject` 返回 null。后续写索引还可能彻底去掉这条记录；项目目录仍在磁盘上，但应用没有恢复入口。

复现：`renameSucceeded=true, nameLength=201, listedProjects=0, loadResult=null, projectFileStillExists=true`。

建议：创建/改名共用名称校验，写入前明确拒绝超限；UI 同步限制。读取已存在的异常记录时保留恢复信息，避免静默过滤；补充 200/201 字符边界测试。

### R2 · P1 · 删除保存失败的项目后，遗留保存任务阻塞整个应用

位置：`src/lib/projectSaveLifecycle.ts:8`、`:14`、`:23`；`src/pages/ProjectCanvasPage.tsx:133`；`src/components/projects/projectDialogLogic.ts:69`；`electron/main.ts:211`。

保存失败的 saver 会在离开页面后保留。此时用户回列表删除项目，删除逻辑没有通知保存注册表；之后重试只能得到 `Project not found`。打开任何项目都先 flush 全部 saver，正常退出也执行同样的 flush，因此已删除的一个项目可以阻塞其他健康项目和正常退出。

复现：模拟一次保存失败，离开并删除 A，再恢复正常磁盘写入；连续三次全局 flush 都返回 `Project not found`，`hasPending=true`，健康项目 B 的文件正常存在。

建议：按项目 ID 管理保存任务，将删除与保存协调为一个操作；删除确认后终止并注销该项目的待保存任务，防止任务继续写入已删除项目。对真实保存失败保留恢复/另存渠道，不能简单忽略所有错误。

### R3 · P1 · 项目元数据缺失被当作空项目，后续保存会删除剩余图片

位置：`src/lib/localProjectStore.ts:108`、`:239`、`:469`、`:404`。

项目已在索引中，但 `project.json` 丢失时，读取使用空快照作为 ENOENT 回退。界面会成功打开一个空画布；用户添加节点后自动保存，清理逻辑会把原 `assets` 下的图片当作无引用文件删除。这会进一步破坏原本还可人工恢复的数据。

复现：在临时项目中移除 `project.json`，加载成功且节点数为 0；保存一个新节点后，原图片目录文件数变为 0。

建议：区分首次创建与已有项目损坏；已有项目元数据缺失/结构异常应报可恢复错误并停止自动保存和图片清理。保留最近一次有效快照或恢复副本。此项只证明故障后的处理不安全，不表示正常写入必然会丢失文件。

### R4 · P2 · 生图超时被当成用户取消，结果节点消失且没有错误提示

位置：`src/services/gemini.ts:64`；`src/components/nodes/usePromptGeneration.ts:222`、`:237`。

内部超时使用无原因的 `AbortController.abort()`，产生 AbortError；任务执行器把全部 AbortError 当作用户取消，删除结果节点，并从失败列表中排除。用户没有点击取消，也会看到等待中的任务突然消失。

复现：把服务层超时缩短为 10 ms，模拟挂起请求；用户的 controller 未取消，服务请求因超时取消，结果节点被删除，父节点 error 仍为空。

建议：明确区分 TimeoutError 与用户取消；只有明确取消才移除占位节点，超时应保留失败卡片、超时说明和重试入口。

### R5 · P2 · 删除最后一个项目后，旧画布可能自动重新导入

位置：`src/lib/projectRepository.ts:227`、`:258`；`src/lib/projectStorage.ts:195`；`src/store.ts:293`。

本地列表为空被视为需要迁移旧 IndexedDB 数据；迁移状态仅保存在 repository 实例内存中，旧数据没有持久化的迁移完成标记。已有本地项目的会话可能尚未执行迁移判断；删除最后一个项目并刷新列表时，遗留画布就会被当作待迁移数据再次导入。

复现：本地有一个项目、IndexedDB 有遗留画布；删除唯一项目后重新 list，列表仍有一个项目，且 UUID 已改变。

建议：持久化迁移状态，区分“首次启用本地存储”和“用户主动删空”；成功迁移后记录源版本和完成状态，不能只靠空列表触发导入。

### R6 · P2 · 大型旧项目迁移仍整批上传，失败后同一实例不再重试

位置：`src/lib/projectRepository.ts:229`、`:235`、`:247`；`src/server/app.ts:49`；`src/lib/imageInputLimits.ts:5`。

此前修复覆盖本地项目读取，但旧 IndexedDB 迁移仍把全部项目、全部图片放进一个 JSON POST。请求限制为 64 MiB，约 48 MiB 原图就可能达到上限。`migrationAttempted` 又在请求成功前被置为 true，导致首次 413 后重试跳过迁移，返回空列表。

复现：内存 IndexedDB 中两份 25 MiB 图片，总原图 50 MiB，生成约 67 MiB 请求；真实 Express 路由返回 413，第二次 list 返回 0 个项目，原 IndexedDB 项目仍存在。

建议：迁移复用逐资产上传与轻量快照提交，并支持断点/失败重试；成功完成后才记录完成状态。无需简单扩大所有接口的请求上限。

### R7 · P2 · 遗留 IndexedDB 镜像写入会反复复制整批图片

位置：`src/store.ts:343`、`:355`、`:358`、`:362`。

旧存储 hydration 成功后，每个 store 更新都会触发 `persistCurrentAssets`。它在异步写入结束后才更新签名，没有排队或合并机制；首个大图片写入尚未完成时，拖动节点等更新会重复提交整个 assets。即使当前项目使用本地文件存储，此订阅仍存在，写入错误也没有 catch。

复现：初始化已有 IndexedDB 历史，加载 1 MiB 图片并在同一写入窗口触发 20 次位置更新，记录到 21 次完整资产写入，复制 21 MiB Base64。该复现不代表所有拖动、所有首次安装都会重复 21 次；触发前提是该旧存储层已 hydration，且前一次写入尚未结束。

建议：本地项目模式关闭不再需要的全局旧画布镜像写入；若仍保留回退模式，应串行合并、增量保存并明确处理配额/写入失败。不要通过修改已成功签名来掩盖写入失败。

### R8 · P2 · 连续粘贴参考图会相互覆盖

位置：`src/components/nodes/useReferenceImages.ts:222`、`:249`、`:257`、`:320`；`src/components/nodes/PromptNode.tsx:332`。

异步读取文件使用调用时的参考图数组，完成后整体回写。上传按钮的 disabled 不能阻止 textarea 上连续粘贴，也不能保护读图期间的删除操作；较晚完成的旧读取会覆盖已完成的新引用。

复现：连续粘贴 A、B，让 B 先读完、A 后读完；两次操作都成功，最终只剩 A 一张参考图。

建议：在提交时读取最新节点状态并原子追加/删除，或按节点排队；数量与总字节限制也应基于提交时状态校验，并防止旧项目会话的回调写入新会话。

### R9 · P2 · 蒙版生成未接入项目退出/节点删除取消生命周期

位置：`src/components/nodes/useMaskGeneration.ts:77`；`src/components/nodes/PromptNode.tsx:197`；`src/components/nodes/ImageNode.tsx:257`；`src/pages/ProjectCanvasPage.tsx:164`。

代码路径确认：两个蒙版生成入口均不传外部 AbortSignal，hook 仅返回服务函数，未注册项目/节点生命周期清理。离开项目时自动保存订阅被取消，但请求仍可能执行；切换到另一个项目后原占位节点已不在 store，结果更新会成为 no-op。若只回到列表，晚到的结果也不再由原页面 saver 订阅。

影响：用户可能继续消耗上游计算，却没有可靠持久化结果或明确取消状态。上游是否计费取决于服务端策略；本轮没有发起收费请求验证。

建议：与普通生图统一任务生命周期；明确“离开即取消”或“后台继续且保存回原项目”的产品行为，并添加项目切换/删除/完成先后顺序的回归测试。

## 值得继续改进，但不混同为已复现故障

1. **大画布资源管理**：分图加载解决了单个超大 JSON，但图片仍全部常驻 Base64，Canvas 的 `onlyRenderVisibleElements=false`，所有节点仍挂载。建议先把任务从节点组件生命周期迁出，再做缩略图、Blob URL 生命周期和可视区域渲染；不能直接打开虚拟化，否则可能重现离屏任务被取消。增加加载进度、取消，以及真实图片解码/内存/帧率基准。
2. **本地 API 的访问边界**：当前默认 loopback、Electron contextIsolation/sandbox、导航限制和基础 CSP 是有效的已有措施；API 尚未统一验证 Host/Origin 或应用会话凭据。可评估 DNS rebinding、跨站请求防护；Image2 URL 校验的 DNS 查询与实际下载解析也未绑定。本轮未完成浏览器攻击链验证，不把这些描述成已证实的远程入侵。显式对外监听时还需独立认证设计。
3. **依赖告警**：将 lockfile 中 qs 更新到修复版本（审计要求至少 6.16.0），核对现有 overrides 和 Express/body-parser 兼容性后运行现有校验。不要用 `npm audit fix --force` 无差别改依赖。
4. **故障可见性与恢复**：增加项目备份/恢复入口、可重试保存错误、带请求 ID 的脱敏诊断；删除已经有 `.trash` 磁盘保留，可补应用内恢复界面。旧审查文档对“离屏不渲染”和“审计零漏洞”的描述已有时效差异，应当保留日期并以本次证据为准。

## 建议修复顺序

实际优先处理 R2–R9 的保存可靠性、任务消失、迁移与重复写入问题；R1 降为低优先级边界项。二进制图片/缩略图/虚拟化作为独立性能改造推进。每项修复优先增加本轮发现的失败场景测试，避免只扩充正常路径测试。
